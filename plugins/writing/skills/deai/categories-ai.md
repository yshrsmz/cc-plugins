# カテゴリ定義: AI生成感（1〜21）

`deai` スキルの検出役 A が使う定義。AI生成文に特有のパターンを扱う。カテゴリ1〜17は文・表現レベル、18〜20は構造レベル、21は読者コンテキストレベル。

一般的な冗長・内容の重複・表記揺れ・文の構成・内容の整合性（カテゴリ22〜26）は検出役 B が主に見る。ここで挙げる箇所が B の担当と重なっても構わない。まとめ役が 1 件に統合するので、担当の境界を気にして指摘を控えないこと。

#### 1. 意義の過剰な強調

- 「非常に重要な」「画期的な」「革新的な」「極めて」「まさに」など、根拠なく大げさな修飾語を使っている箇所
- 実質的な根拠やデータなしに意義を強調している箇所

#### 2. AI頻出語彙

以下のようなAIが好む定型的語彙・フレーズの過剰使用を検出：

- 接続表現: 「さらに」「加えて」「また」「一方で」の連続使用
- 「〜において」「〜に関して」「〜の観点から」の多用
- 「〜を実現する」「〜を可能にする」「〜に貢献する」
- 「包括的な」「体系的な」「効果的な」「効率的な」
- 「多岐にわたる」「多角的な」「多面的な」
- 「シームレスな」「ロバストな」「スケーラブルな」（文脈に合わない外来語）

#### 3. 付け足し構文

- データや事実を提示した直後に、無用な意義づけや解釈を付け足している箇所
- 「〜であり、これは〜を示唆しています」「〜であり、〜の重要性を浮き彫りにしています」

#### 4. 回りくどい繋辞（copula回避）

- 「〜として位置づけられています」→「〜です」で十分な箇所
- 「〜の役割を果たしています」→「〜です」「〜をしています」
- 「〜の一翼を担っています」「〜を提供しています」など、「〜です」「〜します」で済む回りくどい表現

#### 5. 同義語の無意味な循環

- 同じ概念を異なる表現で言い換えて繰り返している箇所
- 「迅速かつスピーディーに」「重要で不可欠な」のような同義の重複

#### 6. 三点セットの強制

- 本来2つまたは4つ以上が自然な列挙を、無理に3つにまとめている箇所
- 3つ目が明らかに水増しや蛇足になっている箇所

#### 7. 定型的な結論パターン

- 「今後の展開が注目されます」「さらなる発展が期待されます」
- 「〜が鍵となるでしょう」「〜が求められています」
- 具体性のない未来への言及で文章を締めくくっている箇所

#### 8. ダッシュ類の過剰使用

- emダッシュ（——）や全角ダッシュ（—）の使用
- 括弧や読点で代替可能な箇所
- 「**太字** — 説明」の形はカテゴリ12 の管轄なので、ここでは指摘しない（修正案が「括弧・読点への置換」ではなく構造の組み替えになるため）

#### 9. 曖昧な出典への言及

- 「多くの専門家が指摘しているように」「一般的に〜とされています」
- 「研究によると」（具体的な研究名なし）
- 誰が言ったか不明な権威への言及

#### 10. 過剰なヘッジング

- 「〜と考えられています」「〜かもしれません」「〜の可能性があります」の連発
- 一文の中に複数のヘッジ表現が重なっている箇所
- 断言できる内容にまで不必要にヘッジをかけている箇所

#### 11. 太字の機械的多用

- 強調の必要がない語句への太字（`**`）使用
- 等間隔で機械的に太字が配置されている箇所

#### 12. インラインヘッダー付き箇条書き・太字の同格挿入

英語技術文書の `**Label:** description` / `**Conclusion** — explanation` をそのまま訳した形。検出対象は次の2形式。

```text
- **ラベル:** 説明文        ← コロン形
- **結論** — 説明文          ← ダッシュ形（全角ダッシュ・em ダッシュ・ハイフン）
```

- **コロン形**は**3つ以上連続**している場合のみ指摘する。1〜2個だけ、または他の形式の箇条書きと混在している場合は自然な使い方として許容する
- **ダッシュ形**は連続数にかかわらず指摘する。日本語では太字で結論を述べてそのまま説明を付記する文はほとんど現れず、1行に停止が2回入って通して読めなくなる
- 地の文・表セルの中の同格挿入も対象にする（箇条書きだけを見ない）

修正案は「一律削除」ではなく、その箇所が何を表現しようとしているかで選ぶ。

| 元の箇所の性質 | 修正案 |
|---|---|
| 論に段差がある（最も多い） | nested list にして、段差をインデントで出す |
| 判定と根拠が対になっている | 2列以上の表に分解する。太字による強調はやめる |
| 1行で言い切れる | 太字を外して普通の文にする（「サイズ上限: 6 MB」→「バッファ応答は 6 MB が上限」） |
| 形式が揃いすぎているだけ | 一部のラベルを外す、またはラベルを文頭に組み込む |
| 用語集・定義リスト的な用途 | そのまま維持する（「語 — 定義」は構造として正しい） |

nested list への書き換え例。

```text
NG: - **キャッシュが必要** — 他の方法では応答時間を満たせない

OK: - 応答時間の目標を満たす手段はキャッシュしかない
        - 事前計算はデータの更新頻度に追いつかない
        - クエリ最適化だけでは 1 桁足りない
```

検査は次の2パターンで行い、修正後にゼロを確認する。

```bash
grep -nE '\*\*[^*]+\*\*\s*—' <file>                    # ダッシュ形
grep -nE '^\s*[-*]?\s*\*\*[^*]+\*\*\s*[:：]' <file>     # コロン形
```

#### 13. チャットボット残留表現・教育的スキャフォルディング

- 「ご参考になれば幸いです」「お役に立てれば嬉しいです」
- 「以下にまとめました」「ご確認ください」
- 「〜について解説します」「〜を見ていきましょう」（導入の定型句）
- 「では〜してみましょう」「まず〜から始めましょう」（教科書的な誘導表現）
- 「筆者」の過剰使用（目安：記事全体で3〜5回以下が自然）

#### 14. 追従的・お世辞的トーン

- 過度に丁寧で当たり障りのない表現
- 読者を持ち上げるような不自然な敬意表現
- 批判や問題点を曖昧にぼかしている箇所

#### 15. 定型的な導入パターン

- 「ここでは〜について解説します」「本記事では〜を紹介します」
- 記事全体の構成を冒頭で説明する不要なメタ記述
- 「〜とは何でしょうか？」のような修辞的疑問文での導入

#### 16. フィラー句

- 「〜に基づいて」→「〜をもとに」
- 「〜の観点から見ると」→ 削除可能な場合が多い

「〜することができる」「〜を行う」「〜という」、なくても意味が変わらない修飾語、回りくどい受動態といった一般的な冗長は、検出役 B がカテゴリ26 で網羅的に見る。ここでは網羅しなくてよいが、AI的な語の癖（同じ語の繰り返し、文脈に合わない副詞など）として目に付いたものは挙げる。

#### 17. コロンの使用（英語的構文）

日本語の文中でコロン（`:`）を使うこと自体が英語的。以下の2パターンを検出する。

**a. コロン導入の箇条書き**
- 「〜は:」「〜する:」のようにコロンで終わる文に続けて箇条書きやテーブル、コードブロックを始めるパターン
- 英語では "The following:" + bullet list は自然だが、日本語では不自然
- 修正案: コロンを句点に置換する。「〜は以下の通り。」「〜がある。」等

**b. 太字ラベル＋コロン（インラインヘッダー）**
- 「**ラベル:**」「**ラベル：**」のように太字テキストの末尾にコロンを付けるパターン
- 英語の "**Label:** description" を直訳した形式
- 修正案: コロンを削除して「**ラベル**」のみにする。日本語では太字だけで見出し効果がある
- **対象は地の文・見出し中のラベルに限る**。箇条書きの「- **ラベル:** 説明文」形式はカテゴリ12 の管轄なので、ここでは指摘しない（カテゴリ12 のコロン形は 3 つ以上連続する場合のみ指摘し、修正案もコロン削除ではなく nested list 化・表への分解・ラベル除去などの組み替えになる）

#### 18. 均一すぎる品質・構造（構造レベル）

- すべてのセクションが同程度の丁寧さ・情報密度・長さで書かれている（人間はセクション長に劇的なばらつきがある）
- すべての論点に解決策が提示されていて、未解決の問題が一切ない（「わかりません」で終わるセクションがあってもよい）
- セクション間の遷移がすべて滑らかすぎる（人間の文章には唐突な話題転換がある）
- 確信度が常に一定（人間は確定的・強い意見・推測・不確実性が混在する）
- 結論が整然としすぎている（未回答の質問や未解決要素がないのは不自然）

#### 19. 教育的すぎる段階的展開（構造レベル）

- V1→V2→V3のような機械的な段階的改善の提示
- 読者への対話が「フォーミュラ通り」に挿入されている感覚
- すべてのコード例が最初から正しく、バグ発見→修正の過程がない

#### 20. 戦略的な不完全さの均等配置（構造レベル）

- 不完全さや注意点が各セクションに1つずつ均等に配置されている（人間はクラスター化する）
- 「あえて不完全にした」感が見える計算された配置

#### 21. 会話の経緯に依存した記述（読者コンテキストレベル）

AI との対話を通じて書かれた文書には、その対話に参加していないと意味が通らない記述が残る。読者は検討の経緯を知らない新規参加者として扱い、読者が持っていない文脈を参照している箇所を検出する。次の4類型に収まる。

| 類型 | 出方 | 修正案 |
|---|---|---|
| 初期案への言及 | 「当初案は」「当初は〜としていたが」「当初リスクとして挙げたが」「最終的に」「結局」 | 採用した結論を最初から提示する形に書き換える。却下した案は比較表の1行として残すか削除する |
| 会話の参加者を指す語 | 「ユーザー確認済み」「ユーザー指摘により」「指示を受けて」 | 読者から見て実在する主体に置き換える（「社内で確認済み」等） |
| 調査・執筆の順序を含む語 | 「付随して判明した」「調査の過程で分かった」「後から気付いた」「あわせて発見した」 | 順序を落として事実だけ述べる。節見出しも同様 |
| 作業ツール由来の注記 | ツール名（WebFetch / grep / subagent）、取得日、「手元の」「実測した環境では」 | 出所が根拠として必要なら手段でなく出所を書く（「公式ドキュメントから逐語取得」等）。純粋な作業ログは削除する |

```bash
grep -nE '当初|最終的に|結局|ユーザー(確認|指摘|の指示)|付随して|調査の(過程|途中)|後から|WebFetch|subagent|手元の' <file>
```

- ヒットが正当なこともある（「当初」が対象システムの歴史を指している等）。機械的に指摘せず、1件ずつ「読者がこの語の係り先を持っているか」で判定する
- 節の並びが**調べた順**になっている場合も指摘する。読者が判断する順（目的 → 前提 → 結論 → 各論 → 未確定）に組み替えると、個々の文から経緯を抜いても筋が通る
- **経緯そのものが内容である文書は対象外**にする。タスクファイル・実行ログ・議事録、および ADR の「却下した選択肢」節のように経緯が構造として定義されている箇所

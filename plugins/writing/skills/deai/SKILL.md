# AI感除去・文章校正スキル

AI生成文に特有のパターンと、冗長・重複・表記揺れ・文章品質・整合性の問題を検出し、自然な日本語に校正するスキル。検出は 2 つのサブエージェント（検出役）に分担させ、本スキルがまとめ役として 1 つの指摘リストに統合する。

## ロール

あなたは経験豊富な日本語ライターであり、AI生成文の特徴を熟知した編集者です。以下の手順で、ドキュメントからAI生成感（AIくささ）と冗長・重複・表記揺れ・文章品質の問題を検出し、自然な日本語に校正してください。

## ワークフロー

### Phase 1: 対象ファイルの特定

1. 引数で渡されたファイルパスを受け取る
2. 対象ファイルを Read ツールで読み込む
3. パスが渡されていない場合は、AskUserQuestion で対象ファイルを確認する

**会話の文脈からファイルを推測しない。** 本スキルは `context: fork` で動くため、呼び出し元の会話履歴が見えない。パスは引数か AskUserQuestion のどちらかで必ず明示的に得る。

### Phase 2: 検出（2 つの検出役に並列で委譲）

検出は観点ごとに 2 つのサブエージェントへ分担させる。1 つのエージェントが全カテゴリを 1 度に見ると、先に見つけた観点に指摘の枠を使い、他の観点が押し出されるため。

| 検出役 | 担当 | 定義ファイル |
|---|---|---|
| A | カテゴリ1〜21（AI生成感） | [categories-ai.md](categories-ai.md) |
| B | カテゴリ22〜26（内容の重複・表記揺れ・文の構成・内容の整合性・一般的な冗長表現） | [categories-quality.md](categories-quality.md) |

**2 つの Agent 呼び出しを 1 つのメッセージで並列に行う。** どちらも `subagent_type: general-purpose`、`model: opus` とし、プロンプトには次をすべて含める。

- 対象ファイルの絶対パス
- 担当する定義ファイルの絶対パス（このスキルのベースディレクトリ + ファイル名）と、「最初にそれを Read し、そこに書かれたカテゴリを網羅的に探す」という指示。もう一方の検出役の担当と重なる指摘を控えさせる指示は書かない（統合はまとめ役が行う）
- 対象ファイルを行番号付きで Read し、文書全体を最後まで確認すること
- 下記の出力形式で指摘だけを返し、ファイルを修正しないこと、AskUserQuestion を使わないこと
- 指摘を返す前の検算: 原文の引用が対象ファイルと逐語で一致するか（`grep -c -F`）、行番号が合っているか、修正案が文書中に無い新しい表記を持ち込んでいないか

検出役の出力形式:

```text
### [カテゴリ番号. カテゴリ名] 指摘タイトル
- **行**: L12（複数なら L12, L40 のように列挙）
- **原文**: 問題のある原文（逐語）
- **修正案**: 具体的な修正後の文
- **重要度**: 高 / 中 / 低
- **理由**: なぜ問題か
```

**検出役も会話の文脈を持たない。** 本スキルは `context: fork` で動き、検出役に渡すのはファイルパスと定義だけなので、どちらも対象の文書を書いた会話を知らない。これがカテゴリ21（会話の経緯に依存した記述）の検出の前提である。経緯を保持している執筆者には「当初案は」「ユーザー確認済み」「付随して判明した」といった記述の係り先が見えてしまい、引っかからない。検出役のプロンプトに、本スキルの呼び出し元の会話の内容を書き加えないこと。

検出役の一方が失敗した、または指摘を返さなかった場合は、その検出役だけを 1 回やり直す。それでも返らなければ、どちらの観点が欠けているかを指摘リストの冒頭に明記して続ける。

### Phase 3: 統合と指摘リストの出力

2 つの検出役の指摘を 1 つのリストにまとめる。**まとめ役は指摘を捨てない。** 行うのは統合・修正案の調整・重要度の調整だけで、検出役が挙げた箇所はすべて最終リストのどこかに残す。修正案が筆者の主張を変えてしまう、別の指摘の修正で解消するなど、適用を勧めない指摘も、重要度を下げて理由にそう書き、一覧に残す。

1. **同じ箇所への指摘を 1 件にまとめる。** 行と原文の範囲が重なる指摘を集め、1 件とし、見出しにカテゴリを併記する（`### [3, 26. 付け足し構文・一般的な冗長表現] 指摘タイトル`。先頭が主カテゴリで、重要度の高い方を主とする）
2. **修正案を 1 つにする。** 併記したすべての観点を同時に満たす案にする。直し方が競合する場合（文ごと削除するか、言い換えて残すか）は、どちらかに決めて理由に書く
3. **修正案が新しい問題を生まないか確認する。** 検出役 B が表記揺れ（カテゴリ23）で揃えた表記と、検出役 A の修正案の表記が食い違っていないか。文書中に無い表記を持ち込んでいないか
4. **引用を検算する。** 残した指摘の原文が対象ファイルに逐語で存在するか（`grep -c -F`）を確認し、存在しないものは直すか落とす

以下の形式で問題箇所の一覧を出力する。各指摘にはカテゴリ番号を付与し、該当する検出項目を明示する：

```text
### [カテゴリ番号. カテゴリ名] 指摘タイトル
- **箇所**: 該当セクション名 or 行の引用
- **原文**: 問題のある原文
- **修正案**: 具体的な修正後の文
- **重要度**: 高 / 中 / 低
- **理由**: なぜ問題か（AI的に感じられる根拠、または冗長・重複・表記揺れ・文章品質・整合性上の根拠）
```

最後に、指摘の要約（カテゴリごとの件数と重要度別の件数）を表示する。カテゴリごとの件数は主カテゴリ（見出しの先頭）でのみ数え、併記したカテゴリは数えない。

### Phase 4: ユーザー確認

指摘リスト出力後、AskUserQuestion ツールで対応方針を確認する。

質問内容：
- 「指摘への対応方針を選択してください」（単一選択）
  - 選択肢1: 「すべて適用」— すべての指摘をファイルに反映する
  - 選択肢2: 「高・中のみ適用」— 重要度が高・中の指摘のみ反映する
  - 選択肢3: 「高のみ適用」— 重要度が高の指摘のみ反映する

ユーザーが「Other」で個別の指摘番号や追加指示を入力した場合は、その内容に従う。

### Phase 5: ファイル修正

ユーザーの回答に基づき、承認された指摘のみを Edit ツールでファイルに反映する。修正完了後、変更箇所のサマリーを出力する。

## 注意事項

- 技術用語や固有名詞は原文を維持すること
- 文体（です/ます調 vs だ/である調）は原文に合わせること
- Markdown記法（見出し、リンク、コードブロック等）は壊さないこと
- 意味や情報が失われる修正は行わないこと
- 指摘の根拠を明確に示すこと（なぜAI的に見えるか、なぜ冗長・重複・不統一・不整合か）
- 過度に口語的にしすぎないこと（自然な書き言葉を目指す）
- 筆者の意図や主張が変わる修正は避けること
- すべてのパターンを機械的に排除するのではなく、文脈に応じて判断すること（例：「さらに」が1回だけなら問題ない）

# テスト精査

担当区画のテストをすべて読み、削除・統合できるものを見つける。編集・テストの実行をせず、根拠を確認できた候補だけを報告する。ユーザーの制約と適用規約に従う。

判断基準は「削除すると、どんな現実的な不具合を見逃すか」の1つだけにする。テスト件数やカバレッジの維持を目的にせず、念のためという理由で残さない。保証の価値と、実行時間・不安定さ・修正負担を比較する。次の6分類に当てはまっても、削除で見逃す現実的な不具合を具体的に挙げられるなら候補にしない。当てはまらなくても、保証の価値が保守コストを明らかに下回るなら候補にしてよい。

- 実装のコピー: 期待値を実装と同じ式・同じ分岐・同じ定数表から計算していないか確認する。実装をそのまま写した期待値は、実装の誤りを一緒に写すため何も保証しない。独立に求めた具体値や仕様の例と比較しているテストは対象外にする。
- モックの自己検証: スタブに設定した値をそのまま検証している、モックが呼ばれたことだけを確認している、被テスト対象のほぼ全部をモックしているテストを確認する。外部への副作用の有無や回数そのものが仕様である呼び出しの検証は対象外にする。
- 型・ライブラリの保証の再確認: 型検査・コンパイラ・null 安全・シリアライザ・フレームワーク・標準ライブラリが既に保証する振る舞いを確認していないか調べる。プロジェクト固有の設定・拡張・アノテーションの組み合わせを確認しているテストは、その設定の誤りを捕らえるかを調べてから判断する。
- 他テストとの重複: 区画外も含め、同じ振る舞いを同じかより強い形で確認しているテストを探す。unit と integration の重複は、どちらが失敗原因を特定しやすく、どちらが安く速いかで残す側を提案する。重複と判断する前に、入力・前提条件・検証している値が実際に同じかを確認する。
- 内部実装への過度な依存: private な関数、呼び出し順、内部状態、ログ文言、生成されたコードの細部に結びつき、振る舞いを変えないリファクタリングで壊れるテストを確認する。公開された振る舞いのテストに置き換えられる場合は、その置き換え先も示す。
- 過剰なケース分け: 同じ分岐・同じ同値クラスを入力だけ変えて繰り返すケースを確認する。境界値、異なる分岐、過去の不具合の再発防止として残されたケースは、それぞれ別の保証として扱う。パラメータ化で件数をまとめられる場合は統合として提案する。

コストは、実行時間（sleep・ネットワーク・実 DB・大きな fixture）、不安定さ（時刻・乱数・並行性・外部依存・retry や skip の指定）、修正負担（無関係な変更で壊れる頻度、snapshot の更新頻度）を具体的に挙げる。実測値がなければ推定と明記し、数値を断定しない。

過去の不具合の再発防止テスト、セキュリティ・権限・データ保護の確認、公開 API や保存形式の互換性の確認は、見逃す不具合が現実的かを特に慎重に確認する。好みやテストの書き方の統一だけを理由にした候補は除外する。

各候補は `テスト（path::name または path:line） / 分類 / 提案（削除・統合先・パラメータ化） / 削除で見逃す現実的な不具合、またはなしと判断した根拠 / 削減できるコスト / 確度（高・中・低） / 関連するヘルパーや fixture` で返す。候補がなければ「テスト精査: 候補なし」と、精査したテストの件数を返す。
